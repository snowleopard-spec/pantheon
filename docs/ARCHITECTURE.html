Project Pantheon

The mini-dex thematic index construction pipeline.

A non-technical guide to how the pipeline turns 8,000 SEC filings into 22 thematic stock baskets.

Companion to docs/Context/PANTHEON_SPEC.md. Written for product managers and analysts who want the shape of the system without the code.

1. What this system does

mini-dex classifies US-listed technology and AI-adjacent companies into 22 thematic sub-indices — “fabless chip design,” “AI-native data-centre power,” “frontier model labs,” and so on — and produces a weighted member list per theme that can be back-tested against real prices. Buckets are non-exclusive: NVIDIA earns weight in several themes at once, in proportion to how much of its revenue plausibly comes from each. The output is a set of frozen CSV/Parquet files plus a manifest. It is a batch pipeline refreshed roughly annually, not a live service.

2. The end-to-end journey of one company

Follow NVIDIA (ticker NVDA) through the seven-stop pipeline.

1. Universe pull. Download the SEC’s master list of every US public filer — ~8,000 companies with tickers, names, and SIC industry codes. NVDA is one entry among banks, biotechs, oil producers, and everything else.

2. Industry filter. A curated SIC range keeps only tech-adjacent names (semis, computers, software, comms equipment, measuring instruments, telecom, data-centre REITs, electric utilities) — ~1,376 candidates. NVDA (SIC 3674) survives; JPMorgan and Pfizer do not.

3. Filing fetch and reading. Pull each candidate’s latest 10-K, the annual filing every US public company files with the SEC. Extract “Item 1: Business” — the plain-English section where the company describes what it sells — plus any structured revenue-by-segment data from XBRL (machine-readable tags inside the filing). For NVDA that gives both the narrative and a segment table (Data Center $47.5B, Gaming $10.4B, ...). Where XBRL is thin, an optional LLM step pulls dollar-quantified splits from the prose.

4. Embedding shortlist. Rather than score NVDA against all 22 buckets, the pipeline first uses embeddings — a technique that turns text into a list of numbers so similar topics land near each other — and cosine similarity, which measures how close two of those number lists are (0 = unrelated, 1 = identical topic). Only buckets above the 0.60 cut-off make the shortlist, typically 1–6 per company. NVDA lands on fabless chip design, AI accelerators, data-centre networking and a couple of neighbours — not foundry or frontier model labs.

5. LLM scoring. Shortlisted (company, bucket) pairs go to the Anthropic Message Batches API. The prompt gives the model NVDA’s Item 1 text, segment table, and just the shortlisted bucket definitions; it returns an estimated revenue share (0–1), a confidence label, and a one-line rationale per bucket. Every company is scored twice independently so QC can catch model disagreement.

6–7. QC and weighting. QC runs sanity checks — anchor companies must score highly on their buckets (NVDA above 0.5 on fabless chip design), the two runs must roughly agree, borderline scores get flagged. Build then converts scores into three parallel weights per bucket (equal, score, cap×score), each normalised to sum to 1. NVDA lands heavy in several silicon buckets and lighter in some software ones, and the whole run is frozen with a manifest.

4. Why the multi-stage design

A tempting shortcut would be to hand each company’s 10-K to an LLM once and ask “score this against all 22 buckets.” The pipeline is deliberately not built that way, and the biggest reason is cost.

1,376 candidates × 22 buckets would be ~30,000 LLM calls, each carrying a full bucket definition. The embedding shortlist collapses that: companies typically match 1–6 buckets, so the LLM sees ~22× fewer pairs. A full run scores ~1,376 companies for $25–$35; without the shortlist it would cost hundreds. Embeddings run locally for free — pushing as much filtering as possible into that stage is the biggest lever on budget.

Segment extraction is the second lever, on accuracy rather than cost. Showing the LLM “Data Center $47.5B, Gaming $10.4B” alongside the narrative anchors its revenue fractions in filed numbers rather than adjectives. When XBRL is silent, the optional LLM segment step recovers what it can from the prose without fabricating.

Third reason is iteration. Every stage persists its output, so cheap stages can be re-run (tweak SIC filter, similarity threshold, embedding model) without re-paying for scoring. Only stage 5 costs money, and it is gated behind a confirmation prompt with a cost estimate. QC and build are pure recomputation — freezing a new index from existing scores takes seconds.

6. The role of each Python file

Each module owns one job and talks to the others only through the database or the file cache. That is the whole reason the pipeline can be resumed, retried, and re-run stage by stage without redoing the expensive parts.

FileWhat it does, in one sentence
config.pyLoads API keys and paths from .env and exposes a single frozen settings object every other module reads.
db.pyCreates and opens the SQLite database and defines the tables (companies, filings, shortlist, scores, batches) plus the latest_scores view.
universe.pyStages 1–2: pulls the SEC master company list, tags each row with an industry code, and marks the tech-adjacent slice as candidates.
edgar.pyStage 3: for each candidate, downloads the latest 10-K, extracts the Item 1 business description, pulls segment revenue from the filing’s structured XBRL data, and records market cap.
llm_segments.pyOptional stage 3.5: for filings where XBRL segments are missing or useless, asks an LLM to extract quantified revenue splits from the 10-K text — refusing to guess if none are stated.
shortlist.pyStage 4: turns each Item 1 and each bucket definition into embeddings and keeps only the (company, bucket) pairs whose cosine similarity clears the threshold.
score.pyStage 5: builds the LLM prompt for every shortlisted pair, submits them via the Anthropic Message Batches API twice for independence, and parses the JSON responses into the scores table.
models.pyPydantic schemas that the LLM output must match — a defensive layer that rejects malformed rows before they touch the database.
qc.pyStage 6: produces a human-readable Markdown report of anchor-ticker sanity checks, run-to-run disagreements, borderline scores, and per-bucket member counts.
indices.pyStage 7: joins scores to market cap, computes three weight schemes per bucket (equal, score, score × cap), and freezes the run to outputs/<date>/ with a manifest.
cli.pyThin Typer dispatcher that maps minidex <stage> commands to the module functions above; contains no business logic.

7. Downstream: prices and returns

Two standalone scripts sit outside the SQLite pipeline and close the loop from frozen weights to actual returns. Both run against any historical minidex_weights.csv.

ScriptWhat it does
scripts/pull_prices.py Fetches adjusted daily closes from Polygon.io for every ticker in a weights CSV, plus the configured benchmark ticker (report.benchmark_ticker in config.json, default QQQ) — 8 concurrent workers, retries 429s, tolerates 404s. Incremental by default. Writes data/prices.csv. Requires POLYGON_API_KEY.
scripts/bucket_returns.py Computes trailing 1y / 6m / 3m / 1m / 1w returns per sub-index as Σ(weight × ticker_return) with per-window renormalisation, plus an annualised Sharpe ratio over a configurable window (default 3 months). Writes an interactive HTML report titled “Pantheon”: a pinned QQQ benchmark row on top, one row per sub-index with the median constituent’s return shown under each weighted figure, and sortable Sharpe and return columns. Click a sub-index to expand its constituent list (ticker, company name, index weight, score, market cap, confidence, Sharpe, returns — company names looked up from data/minidex.db); click a constituent to open its daily price chart (vendored uPlot, inlined — the page stays fully self-contained). A search box under the title covers every LLM-scored company (not just index members): the panel lists all of a company’s scores with below-floor rows tagged, links through to each sub-index, and embeds the price chart for members. A per-member Z column (v2.4) flags each sub-index’s out/underperformers — beta-adjusted abnormal return vs the bucket excluding the member, as a robust z-score — with the top-3/bottom-3 rows tinted green/red in buckets of more than six scored members. Weight scheme comes from report.weight_col in config.json (--weight-col overrides), including the render-time-derived capped scheme weight_cap_score_aug. Also copies this architecture page next to the report so the two link to each other.

This is where iteration lives — the heavy lifting already produced the CSV, so deriving new weighting schemes or return calculations is a small pandas exercise with no pipeline re-run.

8. Configuration knobs (config.json)

Six tuning parameters live in config.json at the repo root, hand- editable without touching code. Secrets (ANTHROPIC_API_KEY, SEC_USER_AGENT) stay in .env. Precedence: environment variable (MINIDEX_<NAME>) beats JSON beats hardcoded default — file-based defaults with per-run overrides. A separate report block in the same file holds the returns-report knobs (sharpe_window, benchmark_ticker, weight_col, weight_cap_m); its _valid_values key documents the accepted values in-file, since JSON has no comments.

Key Default What it controls
embedding_model BAAI/bge-large-en-v1.5 HuggingFace sentence-transformer for the stage 4 shortlist. Default is 335 M parameters (~1.3 GB RAM). Swap to BAAI/bge-small-en-v1.5 (~130 MB) for tight hosts — lower similarity_threshold too since small models produce lower cosine scores.
similarity_threshold 0.60 Cosine-similarity cutoff for stage 4. Pairs above go into the shortlist; anchors are always included regardless. Lower → more pairs scored → higher stage 5 cost, broader recall.
score_floor 0.10 Minimum LLM score required for a company to be included in a bucket's final composition (stage 7). Rows below the floor are dropped as immaterial exposure. Currently set to 0.25 in config.json (raised from 0.10 in v2.1, trimming the frozen composition to 340 memberships across the 22 buckets). Anchor tickers can override the floor via anchor_min_weight.
batch_model claude-haiku-4-5 Anthropic model powering stage 5 scoring and the optional stage 3.5 segment fallback. Haiku is fast and cheap; swap to Sonnet for higher-quality scoring at ~4× the cost.
max_item1_chars 12000 Truncation length for the 10-K Item 1 text sent to the LLM. ~12k chars is roughly 3k tokens — enough for most business descriptions, cheap enough for batch prompts.
anchor_min_weight 0.05 Minimum weight_cap_score for any anchor ticker in its bucket at stage 7. Below-floor anchors are force-included at exactly this weight; above-floor members scale down proportionally. Set 0.0 to disable and use pure cap×score.

9. Outputs

Every pipeline run writes a self-contained set of files to outputs/<asof-date>/:

FileWhat it is
minidex_weights.csv Long-format table, one row per (bucket_id, ticker) member. Includes the LLM score, confidence, market cap, three weight columns (see below), both run rationales, and the prompt/model versions that produced it. The primary artefact for downstream back-testing.
minidex_weights.parquet The same data as the CSV in a columnar binary format. Loads faster in pandas / DuckDB / Spark and preserves numeric precision.
manifest.json Provenance: run date, as-of date, prompt version, model version, embedding model, thresholds, and SHA-256 hashes of the two source artefacts. Reproducibility guarantee.

The three weight columns

Every row carries three parallel weight values, all normalised so each bucket sums to 1.0. Pick one, blend them, or run all three through your back-test.

Column Formula (per bucket) What it captures
weight_cap_score (market_cap × score) / Σ(market_cap × score) Finance-standard cap-weighting, adjusted for thematic exposure. Mega-caps can dominate (NVDA hit ~52% of fabless_chip_design in the pilot). The only column the anchor-weight floor applies to.
weight_score score / Σ(score) Ignores market cap. Weight is proportional to how much of the company's revenue is in the theme — AMD at score 1.0 and NVDA at 0.75 rival each other regardless of cap. Best for pure thematic exposure.
weight_equal 1 / n  (n = members after floor) One share per member. Ignores cap and score magnitude. Naive but a useful diversification benchmark.

From the CSV alone you can derive further variants without re-running the pipeline — square-root or log cap-weighting, blended schemes, or confidence-filtered subsets. The returns report already does exactly this with its fourth, render-time-derived scheme: weight_cap_score_aug caps any single name at m/N of its bucket (m = report.weight_cap_m, default 3; N = member count) and redistributes the excess proportionally until no name exceeds the cap — the frozen CSV is never touched. The heavy work is already done; iterating on weighting is a small pandas script.

10. Hardware

The project has used two very different machines for two very different jobs, and the distinction is deliberate.

Phase one — the heavy run (rare, roughly annual). Computing the weights from scratch — the long filing download plus embedding and scoring — ran on a temporarily rented 8 GB / 2 vCPU DigitalOcean droplet, chosen for two reasons. Availability: stage 3 fetches SEC filings for hours at the SEC rate limit, and a laptop losing Wi-Fi or closing its lid mid-run would corrupt or delay it. RAM: stage 4’s embedding model (BAAI/bge-large-en-v1.5) loads ~1.3 GB, PyTorch adds ~500 MB, and encoder batches push the peak to 2.5–3 GB — beyond what the always-on server could spare. That box existed only for the run: every artefact was copied back, and the droplet was destroyed. (If RAM is ever tight on a future run, swap embedding_model to bge-small-en-v1.5 and lower similarity_threshold to ~0.45 to compensate.)

Phase two — daily operation (now). With the weights frozen, none of that horsepower is needed. The project lives on the existing small always-on droplet (1 vCPU, ~2 GiB RAM, shared with four other services), which is enough because the daily job is just a price pull and an HTML render — the install there deliberately excludes the whole ML stack, and the refresh peaks around 100 MB. That small box refreshes the report every night and serves it privately to my own devices (see the next section). Big machine rented briefly for the rare heavy compute; small machine owned permanently for the daily loop.

11. Daily updates: the droplet and the private network

The returns report no longer waits for someone to run a script. Every day at 22:00 UTC — just after the US market closes — a scheduled job on the existing DigitalOcean droplet (unicorn-hunt) pulls the day’s closing prices from Polygon and re-renders the bucket-returns page. By evening the report is simply current, with no laptop involved.

The droplet runs a deliberately slim install: only what it needs to pull prices and render the page. None of the heavy scoring machinery — embeddings, the LLM pipeline, the SQLite stages — lives there; all of that stays on the Mac. The weights are frozen in definitions/minidex_weights.csv, and the droplet never re-scores anything. It just re-prices the same baskets each day.

The report itself is the v2.1 page described in section 7: a pinned QQQ benchmark row for comparison, an annualised Sharpe column next to the five return windows, the median constituent’s return under each weighted figure, sortable columns, and a price chart behind every constituent row — all in one self-contained HTML file, no external assets.

The rendered page is published to a fixed spot (/srv/pantheon/index.html) and served only over the owner’s private Tailscale network (a “tailnet” — a personal VPN that links your own devices) at https://unicorn-hunt.macaw-dominant.ts.net/. It is real HTTPS with a real certificate, but the address is invisible and unreachable from the public internet. On the iPhone, with the Tailscale app signed in, it opens like any website — and it’s pinned to the home screen like an app. Two pages are published together: the report at the site root and this architecture page beside it as architecture.html. The report’s header links here; the link at the top of this page leads back.

Nothing public changed on the droplet: no new open ports, and the existing public services running there are untouched. The report is reachable only from the owner’s own devices.

When the index is rebuilt (roughly annually), the flow is: re-run the pipeline on the Mac → commit the new weights CSV → git pull on the droplet. The daily job picks up the new baskets automatically from then on.

12. Coherence: do the buckets trade like sub-indices?

The buckets are built from what companies say in their filings. The coherence report (v2.3) asks whether the market agrees: do a bucket’s members actually move together, beyond what the overall market explains?

Method, in one breath. Take each member’s daily returns over the past year, strip out the market component (a regression against QQQ — what remains is the stock’s own movement), and average the pairwise correlations of those residuals across every pair in the bucket. Then compare that number against ten thousand random groups of the same size drawn from the rest of the Pantheon universe. If a bucket sits at the 95th percentile, its members co-move more tightly than 95% of arbitrary same-size groups — evidence the theme is economically real, not just a labelling choice.

Result: the market overwhelmingly agrees. On the current data, 20 of the 22 buckets sit at or above the 95th percentile against their random baselines — even after market movement is stripped out. A sample:

The Hyperscalers result is instructive rather than damning: six mega-caps are a large slice of the market itself, so once the market factor is removed there is little bucket-specific movement left. The report also shows each statistic on raw (un-residualized) returns — the gap between the two columns is how much apparent co-movement was simply market beta. 13. Exception rules and overrides

Two overrides sit on top of the base “score = revenue fraction” rule to handle corner cases it cannot capture on its own.

Pre-revenue exception (Rule 5 of the scoring prompt)

A company with no material revenue but whose principal business purpose is the bucket's defined activity should not score zero. SMR developers like Oklo and NuScale, quantum pure-plays like IonQ and D-Wave, early GPU cloud providers like Nebius — exactly the thematic exposure an index like this exists to capture. Rule 5 supersedes the revenue-fraction rule for these cases: pure-plays score 0.8–1.0, partial matches 0.3–0.7, aspirational-only names (established revenue base talking about future entry) stay at 0.0. Every pre-revenue score is flagged pre_revenue: true with confidence "low" for QC review.

Anchor weight floor (Stage 7 index construction)

Some legitimate anchors still score below the score_floor (currently 0.25) that excludes immaterial exposures. Stage 7 guarantees representation via an anchor-weight floor: any anchor gets at least anchor_min_weight (default 5%) of its bucket's weight_cap_score, even at score zero. Below-floor anchors are hard-fixed at the floor; above-floor members scale down proportionally so the bucket still sums to 1.0. If floors overrun 100%, they split 1.0 equally and everyone else drops to 0. Set anchor_min_weight to 0 in config.json to disable and use pure cap×score weighting.

These two overrides work in tandem. The pre-revenue exception fixes the scoring stage so that pure thematic plays get a real score. The anchor floor is the safety net at the weighting stage — if the LLM still misses a canonical name for any reason (definition ambiguity, run-to-run noise, or a genuinely borderline case), the anchor floor guarantees representation. In the pilot's power_generation bucket, the exception moved Oklo and NuScale from 0.00 to 0.90, and the floor still guarantees them a 5% slot in the final index regardless.
